# roomfordevs

`roomfordevs` — форум для разработчиков. Участники создают публикации, находят их по теме и голосуют; авторы могут редактировать и удалять свои посты. Администраторы дополнительно управляют публикациями и аккаунтами.

## Запуск

Требуется Node.js 20.19+ или 22.12+.

```sh
npm install
npm run dev
```

В режиме разработки `npm run dev` запускает одновременно:

- Vite и интерфейс по адресу `http://localhost:5173`;
- API-сервер по адресу `http://localhost:3001`.

Vite проксирует запросы `/api` на API-сервер. Локально `.env` необязателен: API создаёт случайный JWT-секрет в `data/.jwt-secret`, а CORS разрешает адреса `http://localhost:5173` и `http://127.0.0.1:5173`. По умолчанию SQLite хранится в `data/devroom.sqlite`.

## Публикация на Netlify + Render

Netlify раздаёт frontend, но не запускает этот Node.js API-сервер. Для backend добавлен Render Blueprint в `render.yaml`: он собирает и запускает API, проверяет `/api/health` и хранит SQLite в постоянном диске `/var/data`. Постоянный диск и выбранный план Render могут требовать оплаты; перед созданием сервиса проверьте цену в аккаунте хостинга.

1. Запушьте этот проект вместе с `netlify.toml` и `render.yaml` в Git-репозиторий, подключённый к Netlify.
2. В Render выберите **New → Blueprint**, подключите тот же Git-репозиторий и подтвердите создание сервиса `roomfordevs-api-6adf7fef`. Blueprint генерирует `JWT_SECRET` и задаёт путь к постоянной SQLite-базе.
3. Дождитесь, пока Render покажет статус **Live**, затем откройте `https://roomfordevs-api-6adf7fef.onrender.com/api/health`. Ответ должен содержать `{"status":"ok"}`.
4. `netlify.toml` задаёт `VITE_API_URL=https://roomfordevs-api-6adf7fef.onrender.com`; после добавления/изменения файла запустите **Clear cache and deploy site** в Netlify, чтобы frontend пересобрался с URL backend.
5. Blueprint разрешает CORS для постоянного адреса сайта `https://whimsical-cheesecake-95d8f7.netlify.app` и переданного Deploy Preview. Если у проекта другой постоянный адрес или настроен собственный домен, в Render измените `CORS_ORIGIN` на точный origin сайта (без конечного `/`) и сохраните сервис.
6. Регистрация в production создаёт пользователя в отдельной удалённой базе. Локальные аккаунты, посты и администратор **не переносятся автоматически**; после первой регистрации назначьте администратора через Render Shell командой `npm run admin:promote -- адрес-почты`.
7. Для ИИ-функций отдельно задайте в Render переменные `DOCS_AI_API_KEY` и `DOCS_AI_MODEL`. Ключ добавляется только в настройки Render и никогда не помещается в `netlify.toml` или frontend-переменные.

Deploy Preview URL обычно содержит уникальный префикс перед `--` и может измениться для другого preview. Для постоянной работы используйте основной `*.netlify.app` URL или свой домен и добавьте его в `CORS_ORIGIN`.

Для production задайте переменные окружения:

| Переменная | Назначение |
| --- | --- |
| `NODE_ENV=production` | Включает production-режим сервера. |
| `JWT_SECRET` | Секрет подписи токенов, не менее 32 символов. В production обязателен. |
| `CORS_ORIGIN` | Разрешённый frontend origin (или несколько через запятую), например `https://roomfordevs.example`. В production обязателен. |
| `DATABASE_PATH` | Путь к SQLite-файлу; по умолчанию `data/devroom.sqlite`. |
| `API_PORT` | Порт API; по умолчанию `3001`. |
| `VITE_API_URL` | Базовый URL API, встраиваемый в клиент во время сборки; обычно не нужен при Vite proxy. |
| `DOCS_AI_API_KEY` | Секретный ключ совместимого с OpenAI API; хранить только на backend, не публиковать. |
| `DOCS_AI_MODEL` | Название доступной модели, например указанное в кабинете выбранного AI-провайдера. |
| `DOCS_AI_BASE_URL` | Необязательная базовая точка совместимого API; по умолчанию `https://api.openai.com/v1`. |

AI-помощник не будет генерировать ответы, пока на сервере не заданы `DOCS_AI_API_KEY` и `DOCS_AI_MODEL`. После изменения `.env` перезапустите API. Не публикуйте ключи и не добавляйте `.env` или содержимое `data/` в Git. Production-сборка и запуск API:

`CORS_ORIGIN` должен содержать только источники (схему и домен с портом, без пути), например `https://roomfordevs.example,https://www.roomfordevs.example`. API отклоняет браузерные запросы от других `Origin`. Запросы из Insomnia и других клиентов без заголовка `Origin` продолжают работать.

```sh
npm run build
npm start
```

`npm start` запускает именно API-сервер, а не отдельный сервер статических файлов. Клиентская сборка Vite находится в `dist/` и должна раздаваться веб-сервером или платформой размещения. Команда `npm run build` проверяет типы клиента и конфигураций, собирает интерфейс и компилирует сервер в `dist/server/`. Сервер компилируется после Vite-сборки, потому что Vite пересоздаёт каталог `dist/`.

Другие команды:

```sh
npm run dev:web
npm run dev:api
npm run lint
npm run preview
npm run admin:promote -- user@example.com
```

`npm run dev:web` запускает только интерфейс, `npm run dev:api` — только сервер API с перезапуском при изменении кода. `npm run preview` показывает локальную production-сборку клиента. `admin:promote` выдаёт роль администратора уже зарегистрированному пользователю.

## Как устроено приложение

### Браузерная часть

`src/main.tsx` находит элемент `#root` в `index.html`, загружает глобальные стили и монтирует React-приложение. `StrictMode` помогает выявлять потенциальные проблемы в React-коде во время разработки; в режиме разработки React может дополнительно запускать эффекты, чтобы проверить их очистку. `ConfigProvider` задаёт общую тему Ant Design.

В `src/App.tsx` находятся маршрутизация и основные страницы. `BrowserRouter` включает маршруты без перезагрузки документа, `Routes`/`Route` выбирают страницу по URL, а `Link` создаёт внутренние ссылки:

| URL | Страница и возможности |
| --- | --- |
| `/` | Лента публикаций: поиск по тексту, фильтр темы, сортировка «Популярное»/«Свежее», голосование и пагинация. |
| `/communities` | Каталог заранее заданных тем; фильтрация темы и поиска хранится в URL. |
| `/members` | Реальный постраничный список аккаунтов из SQLite; отображаются только никнейм, дата регистрации и число публикаций. |
| `/assistant` | Персональный ИИ-чат: программные вопросы, чтение собственных публикаций/комментариев и подготовка действий с аккаунтом после подтверждения. |
| `/posts/:id` | Просмотр одной публикации; её автор может редактировать и удалять пост. Администратор может модерировать его в админ-панели. |
| `/users/:username` | Публичный профиль участника и его постраничный список публикаций. |
| `/docs-assistant` | Помощник для составления технической документации; требуется вход и настроенный AI API на сервере. |
| `/submit` | Форма создания публикации; без входа перенаправляет на `/login`. |
| `/login`, `/register` | Формы входа и регистрации. |
| `/admin` | Поиск, постраничный просмотр и управление пользователями и публикациями для администраторов. |

Список тем в интерфейсе задан в `src/App.tsx`, а не загружается как отдельная сущность из базы. Количество участников и онлайна в карточках сообществ — демонстрационные значения. Кнопка «Сохранить» в карточке поста копирует ссылку на публикацию в буфер обмена; отдельного хранилища закладок нет.

`src/components/ui/ActionButton.tsx` объединяет кнопки Ant Design и ссылки React Router с общими вариантами оформления. `src/App.css`, `src/index.css` и `src/features/admin/AdminPanel.css` задают визуальный стиль и адаптацию экранов. При переходе между маршрутами содержимое плавно появляется; карточки ленты и сообществ проявляются с небольшой задержкой. На узких экранах перестраиваются меню и колонки. Анимации учитывают системную настройку уменьшения движения (`prefers-reduced-motion`).

### Backend — серверная часть

Backend в проекте уже есть: это самостоятельный API-сервер на Node.js и TypeScript, исходный файл — `server/index.mts`. Он не использует Express: HTTP-сервер создан средствами `node:http`. В серверной части сосредоточены правила, которым нельзя доверять браузер: проверка входных данных, проверка JWT и ролей, права на изменение и удаление публикаций, SQL-запросы и сохранение данных в SQLite.

Сервер запускается отдельно от React:

- при обычной разработке `npm run dev` запускает API на порту `3001` и Vite на порту `5173`;
- для отдельной работы с API используйте `npm run dev:api`;
- `npm start` запускает собранный API из `dist/server/index.mjs`;
- `npm run dev:web` запускает только интерфейс. Для его работы API должен быть запущен отдельно.

Во время разработки `vite.config.ts` перенаправляет запросы браузера с адресов `/api/...` на `http://localhost:3001`. Поэтому клиент обращается к относительным адресам, например `/api/posts`, а не подключается к файлу базы напрямую. Для размещённого отдельно API клиентский базовый URL задаётся переменной `VITE_API_URL` перед сборкой.

Обработка обычного запроса устроена так:

1. Клиент отправляет HTTP-запрос и, если действие требует входа, добавляет JWT в `Authorization: Bearer <token>`.
2. Сервер разбирает путь, метод, параметры URL и JSON-тело. Некорректный JSON, не-объектное тело и тело больше 1 000 000 байт отклоняются.
3. Для закрытой операции сервер проверяет подпись и срок действия JWT, затем находит пользователя в базе. Для административных операций дополнительно проверяется роль `admin`.
4. Сервер проверяет поля и разрешённое действие, выполняет параметризованный SQL-запрос через `better-sqlite3` и получает результат из SQLite.
5. Клиент получает JSON с данными или объект ошибки и обновляет интерфейс. Ошибки возвращаются с HTTP-статусом; непредвиденные серверные ошибки логируются.

### Защитные меры API

- CORS разрешает только настроенные frontend-origin. В разработке это локальные адреса Vite; в production задаётся `CORS_ORIGIN`.
- Общий API ограничен 120 запросами с одного IP за минуту; вход и регистрация дополнительно ограничены 10 запросами за 15 минут. При превышении API возвращает `429 Too Many Requests` и `Retry-After`. Счётчики хранятся в памяти процесса и сбрасываются при перезапуске; для нескольких экземпляров сервера понадобится общий rate-limit store на reverse proxy или в Redis.
- Размер JSON-тела ограничен 1 000 000 байт; сервер проверяет и `Content-Length`, и фактически прочитанные байты.
- HTTP-сервер ограничивает заголовки 16 KiB, время получения заголовков 10 секундами, получения запроса 30 секундами, неактивности соединения 30 секундами, keep-alive 5 секундами, максимумом 100 запросов на соединение и 100 одновременных соединений.
- API отправляет заголовки `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` и ограничительную Content Security Policy.
- JWT проверяется на сервере, роль пользователя перечитывается из базы, а операции модерации дополнительно защищены серверной проверкой роли.
- Запросы используют параметризованный SQL; пароли хранятся как bcrypt-хеши, а не в открытом виде.

Ограничение запросов применяется к IP-адресу сокета и намеренно не доверяет произвольному `X-Forwarded-For`, который клиент может подделать. Если API работает за reverse proxy, настройте ограничение частоты также на доверенном прокси и корректную передачу клиентского IP. Эти меры затрудняют перегрузку самого приложения, но не могут остановить объёмный сетевой DDoS до того, как трафик достигнет сервера. Для публичного production-развёртывания поставьте перед приложением CDN/WAF или managed reverse proxy с DDoS-защитой, лимитами соединений/запросов и мониторингом. Хранение JWT в `localStorage` означает, что токен доступен JavaScript этой страницы; поэтому не добавляйте в приложение небезопасный HTML и всегда используйте HTTPS в production.

`server/index.mts` также при старте настраивает SQLite, создаёт отсутствующие таблицы и индекс, выполняет небольшую проверку/миграцию старой схемы ролей и добавляет демонстрационные посты только в пустую таблицу. `server/promote-admin.mts` — отдельная серверная CLI-утилита: она напрямую меняет роль существующего пользователя в базе, не является HTTP-маршрутом.

### React-хуки, которые используются

Хук — функция React, которая подключает функциональный компонент к состоянию, жизненному циклу или возможностям React Router. Все хуки вызываются на верхнем уровне компонента или другого хука, а не внутри условий и циклов.

**Хуки React:**

- `useState` хранит локальное состояние интерфейса. Он используется для текущего пользователя; открытости мобильного меню; списка постов, страницы, фильтров, сортировки, загрузки и ошибок; значений форм, режима редактирования и статуса отправки; вкладки, поиска и данных админ-панели; комментариев и состояния профиля. Вызов обновления `setState` сообщает React, что компонент нужно перерисовать.
- `useEffect` выполняет работу, которая связывает компонент с внешним миром, здесь — с API. В `useAuth` при старте проверяется сохранённая сессия. В ленте публикации повторно загружаются, когда меняются сортировка, тема, запрос или страница. В карточке поста данные загружаются при изменении `id` в URL. Админ-панель запрашивает нужную вкладку при смене вкладки, страницы, поиска, роли или ключа повтора. Очистка эффекта помечает запрос как устаревший, чтобы его поздний ответ не обновил уже неактуальный экран.
- `useCallback` мемоизирует функцию загрузки комментариев в компоненте `CommentsSection`, чтобы эффект списка зависел от стабильной функции и обновлялся при смене поста или страницы.
- `useAuth` — собственный хук проекта, построенный на `useState` и `useEffect`. Он возвращает `user`, `setUser` и `checked`: пользователя приложения, функцию обновления пользователя и флаг завершения начальной проверки сессии. Пока проверка идёт, приложение показывает экран загрузки.

**Хуки React Router:**

- `useLocation` читает текущий адрес и помогает подсветить активный пункт бокового меню.
- `useNavigate` программно переходит на другую страницу после входа, создания или удаления публикации.
- `useParams` извлекает `id` из маршрута `/posts/:id`.
- `useSearchParams` читает и обновляет параметры адреса. Лента использует `topic`, `q` и `page`; каталог сообществ — `topic` и `q`. Поэтому фильтр и номер страницы можно передавать ссылкой и восстанавливать после перезагрузки.

`BrowserRouter`, `Routes`, `Route`, `Link` и `Navigate` — компоненты React Router, а не хуки. В проекте не используются `useMemo`, `useContext` или `useReducer`.

### API-контракт и маршруты backend

Общий клиентский контракт находится в `src/types/api.ts`: там описаны пользователь, публикация, голос, ошибки и общий формат постраничного ответа. Входное тело запроса на сервере рассматривается как непроверенное значение и валидируется до записи в базу. SQL-запросы с пользовательскими значениями используют параметры, а не подстановку текста в SQL.

Основные маршруты:

| Метод и путь | Назначение и доступ |
| --- | --- |
| `GET /api/health` | Проверка доступности API. |
| `POST /api/auth/register` | Создание аккаунта и выдача токена. |
| `POST /api/auth/login` | Проверка учётных данных и выдача токена. |
| `GET /api/auth/me` | Проверка текущего JWT и получение актуальных данных пользователя. |
| `GET /api/posts` | Список публикаций; принимает фильтр `topic`, поиск `q`, сортировку `sort`, страницу `page` и размер `pageSize`. |
| `GET /api/posts/:id` | Получение одной публикации. |
| `POST /api/posts` | Создание публикации; требуется вход. |
| `PATCH /api/posts/:id` | Изменение публикации; требуется авторство или роль администратора. |
| `DELETE /api/posts/:id` | Удаление публикации; требуется авторство или роль администратора. |
| `POST /api/posts/:id/vote` | Голос `1` или `-1`; требуется вход. |
| `GET /api/posts/:id/comments` | Постраничное чтение комментариев к публикации. |
| `POST /api/posts/:id/comments` | Создание комментария длиной до 5000 символов; требуется вход. |
| `PATCH /api/comments/:id` | Изменение комментария; требуется авторство или роль администратора. |
| `DELETE /api/comments/:id` | Удаление комментария; требуется авторство или роль администратора. |
| `GET /api/users/:username` | Публичный профиль без email, роли и хеша пароля. |
| `GET /api/users/:username/posts` | Постраничный список публикаций пользователя. |
| `GET /api/users` | Постраничный каталог участников; возвращает только публичные поля. |
| `POST /api/docs-assistant` | Составление документации по явно введённым пользователем задаче и контексту; нужен JWT и серверная настройка AI-провайдера. |
| `POST /api/assistant/chat` | ИИ-чат, ограниченный allowlist-действиями над аккаунтом текущего пользователя; нужен JWT. |
| `POST /api/assistant/confirm` | Выполняет предложенное изменение только после подтверждения владельцем аккаунта. |
| `POST /api/assistant/cancel` | Отменяет ожидающее подтверждения действие. |
| `/api/admin/users` | Постраничный список и поиск пользователей; только администратор. |
| `/api/admin/users/:id` | Изменение роли или удаление участника; только администратор. |
| `/api/admin/posts` | Постраничный список и поиск публикаций; только администратор. |
| `DELETE /api/admin/posts/:id` | Модераторское удаление публикации; только администратор. |

Сервер ограничивает размер списка, проверяет номера страниц и отдаёт число записей и страниц вместе с результатами. Голос пользователя сохраняется отдельно; итоговый счёт публикации рассчитывается из начального счёта и сохранённых голосов. Комментарии хранятся в SQLite; число комментариев публикации рассчитывается по сохранённым записям.

### Комментарии и профили

На странице публикации участник может добавить комментарий, просматривать ответы постранично, а автор комментария или администратор — изменить и удалить его. Сервер проверяет права при каждом изменении, не полагаясь на видимость кнопок в интерфейсе. Удаление публикации удаляет комментарии по внешнему ключу; удаление пользователя также удаляет его комментарии. Публичный профиль показывает никнейм, дату регистрации и число публикаций, но не раскрывает email, роль и парольный хеш.

Каталог участников и число регистраций берутся из таблицы `users`, а количество публикаций считается по таблице `posts`; демонстрационные аккаунты не добавляются. Помощник документации принимает только текстовые поля `task` (до 4000 символов) и `context` (до 16000 символов), доступен вошедшим пользователям и ограничен по частоте запросов. Файлы проекта не сканируются и не загружаются автоматически.

ИИ-чат также требует входа и настроенных `DOCS_AI_API_KEY`/`DOCS_AI_MODEL`. История чата хранится только в состоянии страницы браузера и не записывается в базу. Сервер не передаёт модели email, пароль, хеш пароля, JWT, настройки сервера или личные данные других аккаунтов. Если пользователь просит прочитать свои публикации/комментарии, соответствующие тексты отправляются внешнему AI-провайдеру, чтобы он мог ответить. Создание, изменение и удаление публикаций/комментариев и смена никнейма разрешены только через фиксированный список серверных операций; модель не получает произвольный доступ к SQL или API. Сервер проверяет владельца записи, готовит ограниченное по времени предложение, а действие выполняется только после явного подтверждения пользователя. Передавайте провайдеру только те сообщения и данные, которыми готовы поделиться; не вставляйте пароли, API-ключи или другие секреты. Ответы ИИ могут быть неточными.

### Что происходит при работе с публикацией

Например, при создании поста компонент формы хранит введённые поля через `useState`. После отправки формы браузерный API-helper превращает данные в JSON и посылает `POST /api/posts`; если пользователь вошёл, helper также добавляет JWT. Сервер проверяет токен, поля и ограничения длины, затем записывает пост в SQLite и возвращает созданную запись. Интерфейс получает её ID и открывает страницу этого поста. Редактирование использует `PATCH`, удаление — `DELETE`; сервер заново проверяет авторство или административную роль перед изменением базы. При голосовании сервер записывает или обновляет строку в `votes` и возвращает пересчитанный счёт.

При чтении ленты браузер формирует запрос из параметров URL и состояния сортировки. Сервер применяет поиск/тему, сортировку и `LIMIT`/`OFFSET`, а затем отдаёт текущую страницу и метаданные пагинации. React отображает результат, а при смене фильтра или страницы эффект загружает новый набор. Админ-панель использует отдельные защищённые API-маршруты и такую же серверную пагинацию.

### SQLite и сущности

По умолчанию база находится в `data/devroom.sqlite`. Имя оставлено ради совместимости с существующими данными после переименования продукта. Путь меняется через `DATABASE_PATH`. При первом старте сервер создаёт таблицы и индекс, а демонстрационные посты добавляет только если таблица публикаций пуста.

- `users`: ID, никнейм, email, bcrypt-хеш пароля, роль (`member` или `admin`) и время регистрации. Никнейм и email уникальны без учёта регистра.
- `posts`: заголовок, текст, тема, ссылка на учётную запись автора, текстовое имя автора, начальный счёт и дата создания. `author_id` при удалении пользователя становится `NULL`, а имя автора в публикации остаётся.
- `votes`: пользователь, публикация и значение `1` или `-1`. Составной ключ не позволяет создать больше одного голоса от пользователя на пост; повторный запрос меняет существующий голос. При удалении пользователя его голоса удаляются, при удалении поста удаляются голоса за него.
- `comments`: публикация, автор, текст и дата создания. Комментарии удаляются каскадно при удалении связанной публикации или аккаунта; индекс по публикации и дате поддерживает постраничное чтение.

`users` и `posts` — основные сущности приложения; `votes` и `comments` связывают пользователя с публикацией. Обычный аккаунт создаётся через регистрацию. Администратор может просматривать и удалять участников, а также менять их роли. CRUD публикаций и комментариев выполняется через API и сохраняется в SQLite.

## Регистрация, вход и JWT

1. На странице регистрации или входа браузер собирает данные формы и отправляет JSON-запрос на `/api/auth/register` или `/api/auth/login`.
2. Сервер проверяет email и длину пароля. При регистрации он также проверяет никнейм, хеширует пароль с помощью bcrypt (cost factor 12) и записывает пользователя с ролью `member`. Сам открытый пароль в базу не попадает. При входе email ищется без учёта регистра, а введённый пароль сравнивается с хешем.
3. После успешной проверки сервер подписывает JWT секретом. В токене хранится ID пользователя в поле `sub`, срок действия — семь дней. Ответ содержит токен и профиль без пароля.
4. Браузер сохраняет JWT в `localStorage` под ключом `roomfordevs_token`. `src/lib/auth-token.ts` читает, сохраняет и удаляет его; также при чтении переносит значение старого ключа `devroom_token`, если оно ещё осталось.
5. При загрузке страницы `useAuth` обращается к `/api/auth/me`. API получает токен из заголовка `Authorization: Bearer <token>`, проверяет подпись и срок действия, затем заново читает пользователя из БД. Таким образом, API проверяет роль по текущей записи пользователя, а не доверяет роли из браузера.
6. Все защищённые запросы отправляют тот же заголовок. Сервер проверяет вход и права на каждом действии: одного скрытия кнопки в React недостаточно для защиты. При выходе токен удаляется из `localStorage`.

В локальном режиме секрет хранится в `data/.jwt-secret`, если `JWT_SECRET` не задан. В production нужен собственный `JWT_SECRET` длиной не менее 32 символов. Смена секрета делает ранее выданные токены недействительными. Для размещённого сайта используйте HTTPS и не раскрывайте секрет клиентской сборке.

Чтобы назначить администратором уже существующий аккаунт, зарегистрируйте его и выполните:

```sh
npm run admin:promote -- user@example.com
```

После изменения роли выйдите и войдите снова, чтобы клиент получил свежий профиль. Сервер не разрешает удалить себя из панели, удалить другого администратора напрямую или снять роль у последнего администратора.
